# Tree-RAG 最小实验

这是独立命令行验证，不接入现用知识库页面、业务数据库、用户权限或客户端。没有增加依赖或向量服务；借鉴 PageIndex 的目录导航思路，没有引入其 SDK 或云服务。

## 流程

1. 读取同一目录的 Markdown，保留原文快照、内容指纹、标题层级和行号。
2. 每份文档调用一次入库模型，为已有章节生成不超过 100 字符的摘要，按需简写，不合并或改写原文。CLI 默认入库模型为 `qwen3.8-max`，查询模型独立指定。
3. 查询时先提供完整的精简目录（标题、层级和短摘要），模型一次选出多个节点，通过 `read_nodes` 批量读取原文，自动附带父级原文中的适用条件。
4. 证据充分后通过 `finish_answer` 提交带逐字引文的答案，通常以两次模型调用为目标；确有缺失才补充读取，已读原文不重复返回。
5. 输出实际工具路径、引用文件与行号、调用次数、上游返回的原始 Token 用量。

## 运行

Node.js 24，无需安装新依赖。PowerShell 中配置自己的 OpenAI 兼容接口：

```powershell
$env:TREE_RAG_BASE_URL = 'https://你的模型服务/v1'
$env:TREE_RAG_MODEL = '模型ID'
$env:TREE_RAG_INDEX_MODEL = 'qwen3.8-max'
$env:TREE_RAG_API_KEY = '你的Key'
node apps/server/scripts/tree-rag.mjs index C:/knowledge C:/private/tree-index.json
node apps/server/scripts/tree-rag.mjs ask C:/private/tree-index.json '上海出差住宿标准及审批要求是什么？'
node --test --test-isolation=none apps/server/test/tree-rag.test.js
```

接口地址包括 `/v1`（若服务需要）；模型必须支持 Chat Completions 工具调用和 `tool_choice: required`。文档和摘要会发送到所配模型服务，测试时使用虚构资料。

`TREE_RAG_INDEX_MODEL` 只控制入库，缺省为 `qwen3.8-max`；`TREE_RAG_MODEL` 控制查询。更换模型时应同步检查所配置接口的可用性。正式知识库未来使用管理端选择的渠道与模型，这个 CLI 默认值不是线上配置。

已用现有千问凭据实际验证 Max 入库：一份虚构制度、一次调用、约 10.2 秒、817 Token；三个非空摘要分别为 30、23、26 字符，保留了人员、日期及审批无先后顺序等条件。下方批量性能数据仍来自 Flash，不能当作 Max 性能结果。文件格式解析与扫描件识别尚未接入这个 Markdown 原型，后续需要与上传流程一起实现。

索引包含完整原文，应放在 Git 仓库以外的私有目录，不上传公开仓库。已有索引不会覆盖；资料修改后建立一个新索引文件。查询读取已保存快照，不自动追踪磁盘原文变化。

## 边界

- 最多 20 份文档、每篇 24000 字符、总计 80 个节点、每节 12000 字符；仅识别 `#` 风格标题，忽略围栏代码中的标题。
- 每个问题最多 4 次模型调用、8 次工具调用、累计读取 24000 字符。查询仍会调用大模型，不能把无向量等同于零检索成本。
- 由模型根据精简目录选择相关节点，复杂问题允许多分支和跨文档读取。整个目录随提问发送，因此这版只适用于当前限制内的小知识库，不能直接推算到几千份文档。
- 引文必须属于本次已读取节点并逐字存在于原文。模型需明确标记证据是否足以回答关键问题；证据不足或无引文时固定提示依据不足，不展示无关条款。这个判断仍由模型作出，有引文也需人工核对结论是否受其支持，程序不能保证语义正确。
- 不包含 PDF/Office/OCR、审核发布、跨文档合并、自动冲突判断、权限服务或生产任务队列。不能直接作为多人服务暴露。
- `indexing.usage` 是入库用量，问答结果 `usage` 是各轮用量。缺失的上游用量记为 `null`，不估算金额，不承诺缓存命中。

本工具用于独立比较检索路径和模型表现，不接入线上数据；现用企业知识库、个人本地资料和记忆流程见 [KNOWLEDGE.md](KNOWLEDGE.md)。

## 本次真实模型验证

使用千问 `qwen3.8-flash` 和三份虚构资料，生成 11 个目录节点。首次入库 3 次模型调用，约 30 秒，共 2713 Token；复测直接使用已有索引，没有重新生成摘要。

下表使用同一个模型、索引和三个问题，对比逐步导航与精简目录批量读取；每种数据为单次测量，并非稳定性基准。

| 问题 | 结果 | 模型调用：导航→批量 | 耗时：导航→批量 | 累计 Token：导航→批量 |
| --- | --- | --- | --- | --- |
| 上海住宿标准和凭证 | 找到每晚 500 元、住宿发票及适用条件 | 6→2 | 25.6→7.2 秒 | 13078→3420 |
| 重大项目上海住宿及完整审批 | 关联差旅制度和补充通知，保留两方审批要求 | 4→2 | 24.5→9.2 秒 | 8553→3893 |
| 未提供深圳住宿制度时提问 | 明确提示依据不足，没有编造金额 | 6→2 | 14.0→16.1 秒 | 11996→4189 |

Token 为多轮调用的输入与输出累计，包含重复上下文及缓存命中部分，不代表独立文档大小或实际账单。批量读取后三题缓存输入分别为 1024、2048、2048 Token，未换算费用。三题累计 Token 从 33627 降至 11502，约减少 66%；无答案问题的耗时没有同步降低。

专项本地测试 8 项通过，覆盖父级条件自动读取、重复读取去重、补查、来源引用、证据不足和调用上限。真实模型最初曾将“两方都需审批”说成“先后审批”，收紧“不增加原文未规定的顺序”要求后最终本轮未再出现；这不能保证其他资料不会发生同类问题。两次调用是本次小样本实测结果，复杂问题仍可能补查。

本次只是小样本可行性验证，没有与向量检索在同一测试集上对比，不能证明召回率、费用或速度优于现有方案。

## 简易扩展验证

继续复用原型，使用 8 份虚构 Markdown、9637 字符、30 个节点。加入新旧制度、不同人员标准、连续驻场补贴、长段落、Markdown 表格、无关资料及个人预算干扰。不是 PDF/Excel 解析测试，也不是权限隔离测试。

一次性入库调用 8 次模型，约 81 秒、14691 Token。随后 7 个问题的关键答案和所需来源均符合预设，并人工查看了回答与读取路径：

| 场景 | 调用次数 | 耗时 | 累计 Token |
| --- | --- | --- | --- |
| 现行制度及人员条件 | 2 | 6.9 秒 | 6197 |
| 主制度与补充通知关联 | 2 | 14.1 秒 | 7390 |
| 按历史日期查旧制度 | 4 | 25.1 秒 | 14421 |
| 区分普通员工与总监标准 | 2 | 7.5 秒 | 6493 |
| 区分临时出差与连续驻场 | 2 | 7.9 秒 | 6198 |
| 查长文末尾的保存期限 | 2 | 8.1 秒 | 5762 |
| 无对应制度、排除个人预算 | 2 | 17.9 秒 | 7273 |

单题平均约 12.5 秒、7676 Token。历史制度题曾引用尚未读取的审批节点，被引用校验拦截后补读，因此达到 4 次调用。长文末尾问题只返回对应节点及父级条件，共 75 字符正文，而该文档正文约 4712 字符；这不包含另外发送的目录摘要、工具说明和问题。

资料增多后，完整目录带来的输入用量明显上升。部分回答仍附带问题之外的说明，程序校验只能确认引文存在且已读取，不能逐句保证所有结论均有证据。7 题为人工构造的小样本，不是准确率基准，也没有运行向量方案对照；本轮未修改原型实现、正式页面或业务数据。
